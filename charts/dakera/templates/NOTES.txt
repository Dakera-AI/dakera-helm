== v0.12 features enabled ==
{{- if .Values.dakera.features.multilingual.enabled }}
  multilingual      bge-m3, full-text language "{{ .Values.dakera.features.multilingual.fulltextLanguage }}", query language "{{ .Values.dakera.features.multilingual.queryLang }}"
{{- end }}
{{- if .Values.dakera.features.multimodal.enabled }}
  multimodal        attachments + speech to text (WAV; Whisper model via DAKERA_WHISPER_MODEL, default whisper-base)
{{- end }}
{{- if .Values.dakera.features.vision.enabled }}
  vision            image / page indexing + visual recall (a dedicated store)
{{- end }}
{{- if .Values.dakera.features.records.enabled }}
  records           multi-vector records
{{- end }}
{{- if .Values.dakera.features.lateInteraction.enabled }}
  lateInteraction   colbert-small + MaxSim
{{- end }}
{{- if .Values.dakera.features.rabitq.enabled }}
  rabitq            RaBitQ search mode (latency, not memory)
{{- end }}
{{- if or .Values.dakera.features.multilingual.enabled .Values.dakera.features.lateInteraction.enabled .Values.dakera.features.vision.enabled }}

  These change the embedding model or the lane. On an existing store, multilingual re-embeds it
  in the background (progress: /health embedding_model_change); lateInteraction and vision are
  for a FRESH store: on an existing one the pod exits at startup (the log names both models).
  See the README, "Features in v0.12.0".
{{- end }}
{{- if eq (include "dakera.featuresNeedModels" .) "true" }}

  Models outside the image download into the model cache on first use{{ if .Values.dakera.features.prePull }} (an init container pulls them before the server starts){{ end }}.
  The first start can take minutes: /health/live is 200 meanwhile, /health/ready is 503 with the progress.
{{- end }}
  Check what is on:
    curl http://localhost:3000/v1/capabilities -H "X-API-Key: <key>"
{{- end }}

{{- if and .Release.IsUpgrade (eq (include "dakera.clusterMode" .) "true") }}

== Cluster mode ==
  From 0.12.1 every node needs the same DAKERA_CLUSTER_SECRET. Nodes with and without it, or
  with different values, do not see each other: upgrade every node (release) in one window.
  Check on each node: GET /admin/cluster/status lists the other nodes and the same leader.
{{- end }}

== Server 0.12.2 ==
{{- if eq $ts "0" }}
  Sessions: the server ends no session for inactivity (dakera.config.sessionIdleTimeoutSecs: 0),
  except one started with its own idle_timeout_secs.
{{- else }}
  Sessions now end after {{ if $ts }}{{ $ts }} s{{ else }}4 h (the server default){{ end }} without activity (dakera.config.sessionIdleTimeoutSecs).
  Sessions already idle longer are closed, with their summaries, on the first passes after the upgrade.
{{- end }}
  Key entries ending in * from older versions stay inert until the key is saved again
  (PATCH /admin/keys/{id}); GET /v1/auth/whoami lists them as inert_namespaces.
  Writes are validated more strictly (reserved markers, agent ids over 241 bytes, content over the byte
  limit on update). Server UPGRADE.md, "Upgrading from v0.12.1 to v0.12.2".
{{- end }}

== Next Steps ==

                    including config_warnings)

  Upgrading from chart 0.11.x, 0.12.0 or 0.12.1? Read charts/dakera/CHANGELOG.md first.
  Rolling back to v0.11: see the README, "Rolling back to v0.11" (dakera downgrade runs with the
  0.12.2 image: it rewrites the binary hot-tier records as JSON).
